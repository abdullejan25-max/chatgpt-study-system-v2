# ADR-008: Deterministic private assets and documents

Status: accepted for Phase 6

The asset registry requires an explicit absolute asset root and SQLite database path. Configuration loading creates neither. Source bytes are stored under the root by their SHA-256 digest; `asset://sha256/<digest>` and `document://sha256/<digest>` are the only public addresses. Asset IDs hash original bytes. Document IDs hash media type, source digest, declared text origin, and normalized pages. A title change for the same content identity is a conflict. Repeating the same import is idempotent.

Asset deduplication follows bytes across allowed media declarations. The first validated declaration remains the asset's stored `media_type` and is returned on later registrations; later declarations never rewrite that metadata. It is a record of the initial declaration, not a claim of full file-format validation. Each document separately records the media type used for its ingestion. New document IDs are stable from the declared media type and source SHA-256, independent of extraction/OCR progress; duplicate imports reuse a prior record before PDF parsing. Existing document IDs are preserved when encountered, so adopting the new rule does not require rewriting a private database. UTF-8 is checked for `text/plain`; PDF and image declarations receive only the documented header checks. Public document text and metadata redact absolute Windows paths, including forward-slash UNC paths, while preserving ordinary HTTP(S) URLs and relative references.

Pure UTF-8 text is paginated on form-feed characters. Pages are normalized to NFC and line endings to LF. Heading lines beginning with Markdown `#` split sections, then text is cut into deterministic chunks of up to 1,000 characters. Every chunk carries a stable `chunk://sha256/` URI, document URI, page number, and section. Search is lexical only and bounded to 2,048 indexed chunks; it cannot infer concepts or generate annotations.

`pypdf` deterministically parses bytes and extracts PDF text page by page. A single empty user password is tried for encrypted PDFs, which permits files that open without a prompt while genuinely password-protected files remain unsupported; no password guessing or password input is provided. Bounded in-memory font normalization resolves valid indirect font metric/encoding members before extraction. Unicode sanity checks quarantine clearly suspicious ToUnicode output rather than indexing it as trusted text. The scoped parser configuration bounds declared PDF size, decoded streams and page-tree/XObject work: a PDF is at most 64 MiB and 999 pages, each page/Form content stream at most 1 MB, each font/CMap stream at most 4 MB, and all decoded streams together at most 32 MB. Projected repeated Form XObject expansion has a separate 32 MB budget; invocation count is also bounded. Small inline assets remain bounded to 2 MiB decoded bytes. JPEG/PNG/WebP images registered from a configured local inbox are bounded to 32 MiB; large PDFs continue to use the same root with the 64 MiB PDF limit. The file path is relative to an explicit `[assets].ingest_root`; MCP never accepts an arbitrary absolute path or returns the configured path.

`pdf_text_layer` and `pdf_ocr_derived` identify deterministic extraction provenance, not completeness or visual fidelity. Public `text_layer_status=unverified` means a non-suspicious text layer was extracted but not checked against every visible glyph; suspicious Unicode is quarantined and never indexed. Initial OCR remains quick and bounded: at most eight pages per PDF and 16 attempted pages per ingestion batch, prioritizing no-text pages and then suspicious pages. The rest remain explicit candidates. `list_document_ocr_candidates` exposes their bounded page numbers, and `process_document_ocr_pages` handles up to 16 selected candidates per call, revalidates the immutable source asset, OCRs locally, replaces that page's derived index transactionally, and preserves the document URI. Blank output is tagged `pdf_ocr_empty` and is not indexed; failures remain retryable. Each OCR page is bounded to 12 million rendered pixels at 300 DPI and the document's total extracted text remains capped.

OCR requires the optional `pdf-ocr` extra (PyMuPDF) and `chi_sim+eng` Tesseract language data. With an explicit tessdata directory, the tested PyMuPDF integration does not require a Tesseract CLI executable on `PATH`. OCR output remains derived and may support lexical location only; the original PDF remains authoritative. A standard MCP `document://.../page/{page_number}/image` resource renders one original PDF page as PNG at a fixed 144 DPI, with six-million-pixel and 4 MiB result caps. It exposes only a validated logical document/page ID, not a filesystem path or arbitrary read. Search results include chunk, page, asset, text-origin, and visual-resource logical provenance. This uses MCP's standard binary resource/MIME content, not a Host-specific image protocol. Caller-supplied ordered pages remain explicitly labeled derived input. No generated-model inference is involved.

PyMuPDF is optional and is distributed under AGPL or a commercial license; the optional integration must receive a license review before any release. See the [upstream license notice](https://pymupdf.readthedocs.io/en/latest/about.html#license-and-copyright).

Limits: small inline assets are at most 2 MiB decoded; image files registered from the private inbox are at most 32 MiB; PDFs are at most 64 MiB; one page and one returned page are at most 100,000 UTF-8 bytes; one document has at most 999 pages and 1,000,000 text characters; one batch has at most 16 documents and 65 MiB combined source/text bytes; each OCR continuation has at most 16 pages; a binary asset range returns at most 64 KiB; one rendered page resource is at most 4 MiB/6 million pixels; search returns at most 20 bounded snippets and accepts offset at most 1,000. Inputs are checked before any batch write. SQLite writes use one transaction; newly created blobs are removed when a batch fails. Existing blobs and documents remain intact.

The MCP surface includes `register_asset`, `ingest_documents`, `process_document_ocr_pages`, and (only when an explicit source root is configured) `ingest_document_file` as explicit writes, plus `search_documents`, `fetch_document`, `fetch_document_page`, `list_document_ocr_candidates`, and `fetch_asset` as reads. `register_asset` accepts exactly one of small inline Base64 content or a relative image path under the configured inbox; in both cases only the Gateway validates, hashes, assigns provenance, audits, and persists the unchanged source bytes. Path mode supports one asset per call so a multi-image task registers each original separately. Page text/image are standard resource templates. All ingestion/derived-data tools require the `ingest` capability; reads require `read`. The file channel is a bounded local source-root alternative, not an arbitrary filesystem read capability. Exposing write tools to an untrusted remote host remains outside this local deployment's security boundary.
